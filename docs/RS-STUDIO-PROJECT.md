# 1. Visão do Projeto

## Projeto

Landing page profissional da **RS Studio**.

## Objetivo

Criar uma landing page profissional para apresentar a RS Studio, seus serviços e projetos, servindo como presença digital e portfólio para captação de clientes.

O projeto também será utilizado como projeto prático para desenvolver competências em:

- HTML
- CSS
- JavaScript
- Tailwind CSS
- Git e GitHub
- Scrum
- Desenvolvimento web
- UX/UI
- Organização e documentação de projeto

## Posicionamento

A RS Studio pretende apresentar serviços relacionados a:

- Desenvolvimento web
- Design gráfico
- Identidade visual / logos
- Landing pages
- Banners e peças digitais
- Projetos de Unity / VR

- Depois que o contexto do projeto foi colocado nas fontes do projeto, o desenvolvimento fluiu melhor.

### Sprint Retrospective

**O que funcionou bem**
- A escrita e definição do conteúdo foi uma parte produtiva da Sprint.
- As explicações foram claras e objetivas, sem excesso de informação.

**O que deve melhorar**
- Quando forem fornecidos trechos de código para copiar, devem ser apresentados em blocos de código com linguagem indicada (por exemplo, `html`), para permitir realce de sintaxe e facilitar a leitura. Evitar apresentar código como texto simples.
- Os testes devem ser proporcionais ao risco e focados, em primeiro lugar, nos trechos alterados e nos seus efeitos diretos. Uma revisão global só deve ser pedida quando houver alterações transversais, antes de uma entrega importante ou quando existir uma razão técnica concreta.
- Ao retomar o projeto depois de uma pausa ou noutro dia, confirmar a data/contexto e o estado da tarefa antes de pedir testes repetidos. Usar a data disponível na conversa como referência, sem presumir que o trabalho foi feito no mesmo dia.
- No início de cada tarefa, fornecer instruções mais completas: objetivo, ficheiros envolvidos, passos de implementação, critérios de aceitação, testes necessários e versionamento esperado. O utilizador poderá pedir esclarecimentos pontuais durante a execução.

**Ações a aplicar na Sprint 3 e seguintes**
1. Fornecer instruções completas no início de cada tarefa, sem exigir que o utilizador espere por cada passo individual.
2. Entregar código em blocos formatados e identificados pela linguagem.
3. Testar apenas as áreas alteradas e os fluxos diretamente afetados, expandindo os testes quando o risco justificar.
4. Incluir o versionamento no plano de conclusão de cada tarefa que altere ficheiros: `git status`, revisão com `git diff`/`git diff --staged`, `git add`, `git commit` e `git push`, conforme aplicável.
5. No regresso após uma pausa, confirmar o estado atual antes de repetir verificações já realizadas.

# 7. Git Convention

## Tipos de commit

### feat

Nova funcionalidade.

```text
feat: create navigation header
```

### fix

Correção de problema.

```text
fix: correct mobile navigation spacing
```

### style

Alterações visuais ou de formatação que não alteram comportamento.

```text
style: improve hero layout
```

### refactor

Reorganização ou melhoria interna do código sem alteração do comportamento esperado.

```text
refactor: simplify navigation structure
```

### docs

Documentação.

```text
docs: update project context
```

### chore

Manutenção ou configuração.

```text
chore: configure tailwind
```

## Convenção de idioma

As mensagens de commit devem ser escritas em **inglês**.

Exemplos reais utilizados/esperados:

```text
feat: add footer
chore: review and validate sprint foundation
```

## Fluxo básico

```bash
git status
git add .
git commit -m "tipo: descrição"
git push
```

# 8. Convenções de desenvolvimento

## HTML

Priorizar HTML semântico.

Exemplos:

- header
- nav
- main
- section
- article
- footer
- button
- a

Evitar utilizar divs indiscriminadamente quando um elemento semântico adequado existir.

## CSS

Utilizar Tailwind CSS como principal ferramenta de estilização.

O CSS global deve permanecer mínimo e reservado para regras que façam sentido fora das classes utilitárias.

## JavaScript

Utilizar JavaScript apenas quando houver necessidade de comportamento ou interação.

O HTML da página não deve ser gerado pelo `main.js` sem uma necessidade específica.

## Responsividade

A página deve ser construída pensando desde o início em:

- Desktop
- Tablet
- Mobile

As classes responsivas do Tailwind devem ser utilizadas quando forem necessárias alterações de layout, tipografia ou espaçamento entre breakpoints.



- Tornar o Sprint Planning mais detalhado a partir da Sprint 2.
